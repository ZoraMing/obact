# Obact 第一阶段开发计划

基线：[PRD v1.5.3](PRD.md)。本文把 PRD 第 4、9、10 节整理成可执行的开发计划，供多个 agent 并行开发。需求编号（FR-xx）、测试编号（F/T/R/BW/C/E/TS/RS）均沿用 PRD。

## 1. 总览

第一阶段交付一个本地、跨平台的浏览器观察与操作工具：把网页整理成带编号的可操作元素，按 JSONL 工作流稳定回放，崩溃可续跑，单次提交零重复，并留下研究用轨迹。不接入 AI。

```
M0 契约与脚手架 → M1 观察与执行内核 → M2 工作流引擎 → M3 录制器与人工接管 → M4 服务、并行与接口 → M5 真实任务与验收
```

### 当前能用什么

可以直接用的是内核库 `packages/core`（`observe`、`act`、定位器生成、浏览器池），用法见 [README](../README.md) 的“试用”一节。还没有的：服务与统一接口（M4）、JSONL 工作流引擎（M2）、录制器（M3）、Python 客户端（M4）。也就是说现在能对任意网页“看”和“动手”，但还不能把一串操作存成工作流、断点续跑，也没有 `obact` 命令行和 JSON-RPC 服务。

技术基线：TypeScript（Node ≥ 22.18）+ puppeteer-core 25.12；Chrome for Testing 141.0.7390.122（暂定，见第 7 节）；Python 做客户端与评测；存储用文件，不引入数据库。

### 3.1 M0 预研项

1. 扩展加载：固定版本的 Chrome for Testing 下，Puppeteer 能否加载 MV3 扩展并保持侧边栏连接。
2. 服务管理的浏览器：任务子进程连接已运行浏览器，并在 DOM 上写入元素编号属性，确认 iframe / Shadow DOM 下可行。
3. MiniWoB++ 接入：本地起页面、读 reward 的方式，以及 BrowserGym 提取结果的导出方式（供 BW-14）。

结论见 [M0 预研结论](spikes/M0-spikes.md)，要点：

- **进程模型可行**：任务子进程被杀后浏览器与页面不受影响，新进程可接管；同一配置目录重启后登录态保留。
- **编号**：页面脚本 + CDP 能覆盖主文档、同源和跨域 iframe、开放和封闭 Shadow DOM；但整块克隆重绘会把编号属性带到新节点上，所以编号必须以 backendNodeId 为准，属性只用于各视图对齐。
- **observe 性能**：全量可访问性树在 1 万个可交互元素时要约 3 秒，因此默认只取视口内元素的可访问性信息。
- **扩展**：用 `--load-extension` 可行，已在 Chrome for Testing 141.0.7390.122 上复核（无头和有头）；Puppeteer 的 `enableExtensions` 在开调试端口时不可用。
- **MiniWoB++**：静态托管即可，由 Node 驱动、读取它自带的奖励；BrowserGym 的提取函数可以导出 BW-14 基线。

## 6. 并行开发规则

1. 各模块只依赖 `packages/schemas`，不直接引用其他模块的内部实现。
2. 改 Schema 必须同步更新契约测试与样例；冻结后的破坏性改动需评审。
3. 每个模块随代码提交夹具测试；每次提交跑 F、T。
4. 定位器生成逻辑只有一份（core），录制器与回放共用。
5. 单次提交在任何路径下都不自动重试；新增动作类型时必须声明是否属于单次提交。
6. 敏感参数（名称含 password、token、secret）在日志、留痕、返回结果中一律显示为 `***`。
7. 浏览器版本与测试环境见 PRD 8.3：测试固定用基准版本，`npm run browser:install` 安装，不得在 helper 里悄悄回退到别的浏览器。
8. 测试要少而有价值：每条测试要对应一个需求或一个真实发现过的问题；只验证“能跑”、重复覆盖同一行为、靠时间碰运气的不写；写出的测试必须能稳定通过，不稳定的先修或删除。
9. 开发分支 `claude/gallant-clarke-1nm8la`，提交说明写明涉及的 FR / 测试编号。
