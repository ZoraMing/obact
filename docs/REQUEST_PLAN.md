 
### 航班查询
> 使用项目规范编写使用的demo,查机票,获取 https://flights.ctrip.com/online/channel/domestic 进入携程查询深圳到上海七天后最便宜的5个航班号,存到文件

编写这个查机票 demo 过程中暴露出来的体验问题非常典型，主要集中在反爬拦截、复杂动态网页抽取、模板能力不足以及文件导出工具链割裂四个方面。
一、为什么觉得这么难用

1. 反爬对抗与浏览器兼容问题
携程等主流网站有严格的风控体系（如网宿 CDN 432 状态码和自研 whaleguard 系统）。
项目默认配置的测试版 chrome-headless-shell 缺少真实浏览器特征，且暴露了自动化标识，访问携程会直接被拦截并显示 whaleguard block。
当切换到系统安装的完整 Chrome 时，底层 CDP 在初始化新标签页和关闭默认空白页时容易产生竞争，导致 detached Frame 异常直接让进程崩溃。
2. 动态业务参数无法直接声明
用户需求是查询七天后的机票，而当前工作流的模板引擎只支持直接读取预设变量，无法在步骤配置里完成类似当前时间加七天并格式化为年-月-
日的动态计算，迫使开发者必须退回编写自定义脚本。
3. 复杂页面观察信息噪声过大
页面分析工具生成的快照文本会为数千个 DOM
节点编号，面对现代大型单页应用时输出动辄被截断，难以直观推导可用的定位器。同时携程列表使用虚拟滚动，未滚入视口的航班元素并不存在于 DOM 中。
4. 接口截获在大体积响应下失效
携程的航班数据其实都在一个 batchSearch 接口中，但因响应体数据量很大，CDP 底层常报请求内容被缓存逐出（evicted from inspector cache），导致通过网络截获取不到完整   
JSON，只能回退去解析页面 DOM。
二、写到文件时有哪些问题
1. 核心库与工作流引擎的文件写入割裂
项目在 packages/workflow 内部实现了一套按日期分目录、带主键去重索引以及追加写入的功能，但核心库 packages/core 并没有暴露这些能力。当开发者以脚本形式编写 demo     
时，必须自己调用 Node 原生文件模块，处理建目录、序列化、格式转换等重复逻辑。
2. CSV 编码与格式处理容易踩坑
直接写入 CSV 文件在 Excel 等工具中打开经常出现中文乱码，必须手动处理 UTF-8 BOM 头，且字段中包含逗号、特殊字符时需要额外转义。
3. 动态加载下的去重与完整性难以保障
在虚拟滚动场景下，页面边滚动边渲染，旧的卡片会从 DOM 中移除，新的卡片会重复出现。如果直接写入文件容易产生重复记录或遗漏，需要自行维护内存 Map 过滤。
三、如果能提供哪些功能会更好编写

1. 开箱即用的反爬防检测预设
在 launchBrowser 配置中增加防检测模式（如 antiDetection 或 stealth: true），自动抹除 navigator.webdriver
标识、补充真实插件与语言列表，避免每次手动拼装参数。同时完善多标签页管理，避免完整 Chrome 下的 frame 分离异常。
2. 时间与常见表达式模板
在模板解析层支持基础的日期偏移与格式化，例如允许在工作流中直接写：
{{date: +7d, format: YYYY-MM-DD}}
这样无需借助外部脚本计算即可纯配置驱动查询未来日期的任务。
3. 统一的数据导出辅助工具
在 core 或 workflow 导出通用的数据落盘工具函数，例如：
saveOutput({ filename: 'flights', data: list, formats: ['json', 'csv'], key: 'flightNo' })
统一处理 UTF-8 BOM、去重和路径规范检查。
4. 列表与卡片抽取增强
强化抽取步骤（extract）对卡片容器的感知能力，支持声明卡片根节点及内部相对字段，并内置按滚动距离自动收集去重的机制，无需手动写复杂的 evaluate 查找逻辑。
5. 调大 CDP 网络响应缓存限制
允许在会话配置中设置网络响应缓存上限，避免大型 JSON 接口因超出默认缓存而无法读取，这样像携程、电商这类直接返回完整数据的接口就能一键截获。

除了前面提到的反爬、大响应体截获和日期计算之外，在实际编写和执行类似携程这种真实业务流程时，还存在以下深层次的痛点：

一、元素交互与复杂表单定位方面
1. 缺少卡片作用域定位能力
现有的定位机制是全局扁平查找。但在航班列表、商品列表等卡片场景中，页面通常有几十个结构完全相同的项。想要定位特定航班卡片内的预订按钮或价格，全局定位器很容易匹    
配到多个元素并报重复错误，必须退回写深层 CSS 选择器或通过脚本遍历 DOM 祖先节点。
2. 现代前端框架的输入绑定难触发
携程等站点的出发地、目的地输入框和日历组件绑定了复杂的内部状态。简单的填值动作只改写了输入框的显示属性，往往无法触发前端框架的双向绑定事件，导致光标离开后输入    
内容立即被重置为空。
3. 伴随浮层与遮挡物干扰严重
许多站点在聚焦输入框时会自动弹出推荐城市或历史记录浮层，或者中途弹出新人优惠券、会员协议弹窗。这些浮层极易遮挡目标元素或拦截点击事件，导致框架直接报遮挡错误，    
缺乏通用的非预期浮层处理机制。
二、页面加载与等待机制方面

4. 动态渲染与骨架屏难以准确判断就绪
现代页面广泛采用骨架屏、组件异步分块加载以及局部数据刷新。现有的基于特定元素出现或固定超时的等待方式非常脆弱，往往骨架屏 DOM
已经出现但真实数据还没填充，或者数据已经到位但动画还在执行，容易导致提前抽取到空数据。
5. 单页应用的客户端路由感知缺失
用户点击查询后，许多单页应用并不发生整页刷新，而是通过前端路由局部更新数据。框架对这种页面局部切换缺乏明确的生命周期状态通知，开发者很难精准判断接口请求是否已    
经全部结束、新内容是否已经完全挂载完毕。
三、数据抽取与清洗转换方面
6. 抽取字段缺乏内置清洗管线
现有的抽取功能只能获取原始 DOM
文本。拿到的数据通常是类似含货币符号、起字或机型混合的杂乱字符串，无法在声明抽取规则时直接通过正则提取纯数字、去除前后缀或做格式标准化，只能全部拿到后再单独写    
后处理代码。
7. 跨层级与展开详情的数据难以合并
航班的仓位、行李额、退改规则通常需要点击展开后在折叠面板或弹层中展示。现有的列表抽取机制无法支持点击展开子项、提取子项详情、再将子项与父卡片扁平合并的操作。      

四、调试排查与流程韧性方面

8. 报错后缺乏现场保留与交互排查机制
工作流一旦在某一步失败，环境便迅速退出或进入终止状态。开发者无法在报错发生的精确时刻直接在浏览器中打开开发者工具审查当前页面的
DOM、网络请求与控制台报错，只能反复重新运行并依赖截图盲猜原因。
9. 错误处理粒度太粗，缺少业务级降级分支
控制流对于失败的处理基本局限在停止、跳过或转人工，无法根据具体的错误原因执行业务降级逻辑。例如当直达航班列表为空时自动尝试查询中转航班，或者某一步元素失效时切    
换备用交互路径，流程的整体容错能力较弱。
10. 留痕信息中缺少上下文关联诊断
日志记录主要记录了动作名称、耗时和简要结果，当发生超时或定位不到元素时，日志中缺少当时视口的局部 DOM
快照、目标元素当时的可见性状态以及页面未完成网络请求的清单，排查定位问题耗费时间。

缺少嵌入计算脚本
1. 缺少行内计算与脚本步骤
当前工作流的模板引擎只支持纯粹的变量查表替换，比如读取静态配置或外部传入的参数。它不支持任何动态计算或表达式求值。像今天加七天并格式化为日期字符串这种常见的计    
算，在纯 JSONL 工作流里完全无法表达。如果要用工作流，只能强行要求人工在启动命令里手动传入计算好的日期参数，无法做到自包含地独立运行。
2. 页面执行脚本无法回传给流程变量
虽然底层动作支持在页面里执行一段脚本，但执行结果并没有被工作流引擎设计成可以回传保存为后续步骤的变量。这导致即使可以在浏览器端用 JavaScript 算出日期或拼出        
URL，也没办法把结果提取出来供接下来的跳转步骤使用。
3. 缺少内存数据的清洗与排序算子
任务要求获取最便宜的5个航班。在工作流体系里，抽取步骤负责从页面抓取数据并直接落盘。但工作流缺乏对数组的后处理算子，比如按价格字段升序排序、去重、截取前5条等。    
即便抽取出了页面上所有的航班数据，工作流也无法在内存中把最便宜的前5个筛选出来并单独写入文件。
4. 真实业务场景下的反爬参数与流程控制需要代码级灵活度
携程有严格的风控拦截，启动浏览器时需要额外注入反检测参数，并且在页面加载、滚动懒加载和异步渲染时，需要根据实际返回情况做灵活的条件判断与重试。纯声明式的 JSON     
步骤在面对这类复杂的单页应用时表达能力受限。

1. 现代单页应用的“半就绪幽灵状态（Ghost State）”痛点
传统网页的数据是一次性随 HTML 吐出来的，DOM 在就代表数据在。
而现代前端（React、Vue、Next.
js）为了极致优化首屏加载指标，广泛采用分批延迟渲染：页面先渲染卡片外壳和骨架，价格先填上去，但具体的机型、经停信息甚至航班号由另一个次级接口延后数秒填入。        
自动化如果只看容器是否出现、或者只看表层可见文字，就会精准踩进这种“外壳已到位、内部关键字段还是空的”半就绪状态，造成字段漏采并进而触发过滤逻辑把有效数据丢弃。    
自动化框架普遍缺乏“业务字段级就绪感知”。
2. 宿主桌面环境与容器化自动化参数的冲突痛点
很多自动化框架的底层启动参数直接照搬了 Linux CI 或 Docker 容器无头环境下的设定（如直接禁用 GPU、固定小分辨率）。
当把这套配置搬到真实的 Windows/macOS
桌面进行有头回放时，强行禁用硬件加速或者缺乏窗口激活，会触发桌面显卡驱动的不兼容或浏览器的后台休眠机制，导致窗口黑屏或无重绘。自动化配置缺乏针对有头桌面与无头    
容器的自适应环境分层。
3. 过度依赖“可见文本”，忽视 DOM 元数据的脆弱性
大多数通用自动化和 AI 识别工具习惯于将页面扁平化为纯文字来观察（如通过 innerText、Accessibility 树或 OCR）。
但真实商业网站在前端架构上，为了反爬防护、避免全局重绘或支持打点追踪，往往会把最稳定、最精确的业务主键编码在元素 id、data 属性或 class
中，而在表层文字上做样式混淆或延迟渲染。单一依赖可见文本的做法在对抗现代前端架构时显得十分脆弱，必须具备属性、文本、接口网络多层回退提取的机制。

纯声明式的 JSONL 或 YAML 适合用来描述稳定的页面动作序列（打开、点击、等待、输入、抽取），但它永远无法穷举所有具体的业务计算与数据加工逻辑。
在成熟的自动化工程中，通常正是通过在工作流的两端或中间引入轻量脚本辅助来完美配合的：
一、前置脚本辅助（参数生成层）
在工作流启动之前，由一个极简的脚本负责动态参数的计算。
例如在运行查机票工作流前，前置脚本计算出当前日期加七天、格式化为目标字符串，然后自动作为变量传给命令行启动工作流：
cli.ts run ctrip_flights --var dep_date=2026-11-02
这样工作流本身保持干净和确定性，而易变的业务规则由外部前置脚本灵活供给。

二、中间步骤的行内脚本（Code Step 算子）
工作流引擎自身支持扩展一个轻量的脚本步骤（例如 op 为 eval 或 script）。
允许工作流在步骤之间执行几行简短的代码，输入上文的变量，计算完成后把返回值重新存入变量字典供后续步骤消费。像 GitHub Actions 的 run 步骤或各类工作流系统里的       
Function 节点，都是这种思路。

三、后置处理脚本（数据转换与管道）
遵循经典的 ETL 分工原则：
工作流引擎专心负责 Extract（抽取）：负责利用浏览器对抗风控、做检查点续跑、把原始航班数据全量抓下来存入中间文件；
后置脚本专心负责 Transform（清洗与排序）：在数据落地后，由一个简单的后处理脚本读取数据文件，执行按价格升序排序、截取最便宜的前 5 个、生成特定格式报表。

### 网页搜索
> 要求是进入www.google.com ,点击输入框,输入汉堡,点击搜索, 再得到的回复中选择第二个选项进入,给出对应页面标题内容到本地output文件

这个工具目前在手写编写流程时体验确实不够友好，手写 steps.jsonl 与 workflow.json 主要存在以下几个根本性的痛点和设计问题：

一、为什么手写会觉得难用

盲盒式编写，全靠猜网页结构 现代大型网站（如 Google）界面结构高度动态。比如搜索汉堡后，页面顶部直接弹出了大面积的 AI 概览卡片，普通网页结果被推到了下方。手写步骤时我们无法直观看到页面内部的 DOM 树和选择器层级，只能凭经验猜测，一旦猜错（如 nth-child 结构对不上），耗费时间执行后报错找不到元素，调试成本很高。

定位机制严格，容错和灵活性不足 项目为了防止误点产生误操作，定位器采用了严格的唯一性断言。如果一个选择器在页面上能匹配到多个元素，或者层级不对，就会立即中断抛错，而不支持类似获取第几个结果或备选候选链机制。

底层细节容易阻碍主流程 例如现代 Google 搜索框已经改版成了 textarea 并带有 combobox 角色，框架底层此前把 combobox 只归类为 input，导致执行 fill 填写时被框架判定为只读输入框拦截；再比如 Chrome 初始化时关闭默认标签页会触发 frame detached 竞争等，这些特异性增加了试错成本。

JSONL 格式对人工手写不友好 单行 JSON 语法极其严苛，嵌套深且缺乏 IDE 语法补全与类型提示，手写错一个字段名或标点就会解析失败。

二、写到文件带来的具体问题

缺乏调试反馈循环 常规写代码可以通过断点单步执行，而手写步骤文件时，每修改一步，都必须重新经历打开浏览器、加载页面、输入、搜索的完整过程，不能停在出错的当前页面即时修改并直接验证。

静态选择器难以应对动态 A/B 页面 不同网络、不同时段访问 Google，有的出 AI 概览卡片，有的直接出搜索列表，死写静态选择器在动态多变的真实网页中非常脆弱。

三、如果框架能提供哪些功能，编写体验会大幅改善

交互式录制与元素拾取器（Recorder / Inspector） 提供一个命令启动浏览器并开启拾取模式，用户在页面上点击哪里、输入什么，命令行直接自动生成标准规范的 steps.jsonl，并自动计算出最优的唯一定位器，彻底无需人工去审查 DOM。

单步调试与 REPL 交互模式 当步骤执行报错进入 NEED_HUMAN 时，保持浏览器窗口开着，允许在终端中即时输入新的动作或选择器直接在当前页面执行并验证，验证通过后一键追加写入文件，避免反复重启。

更加人性化的语义定位与索引支持 支持直接按可见文本或序号选取，例如 target: { text: "汉堡", index: 2 }，直接点击页面第 2 个结果，而不需要人工编写复杂且脆弱的 CSS nth-child 选择器；同时支持备选定位器列表，前一个找不到自动尝试后一个。

TypeScript 强类型 DSL 支持用 TypeScript 编写工作流代码，通过 IDE 自带的类型推断实现自动补全和参数检查，并在编译期拦截非法参数。

智能一键抽取 在 extract 阶段提供开箱即用的预设模式，例如直接提取当前页面所有标题或指定卡片，而无需人工逐个配置 root、item、fields 等繁琐结构。

定位器设计过度防错，缺少相对索引（nth）。 底层定位器要求目标元素在页面必须是唯一的。当搜索结果列表里有多个相同结构的卡片时，定位引擎看到多个匹配项就会直接报错抛出 not_unique。因为定位器契约里没有提供像 nth 或 index 这种指定第几个元素的能力，导致写步骤时为了绕过报错，被迫去看页面上当时展示的具体文字，用特定文本去做唯一匹配。

对比 MCP Chrome 的设计，结合在携程机票任务中遇到的各种实际卡点，可以从以下五个维度学到非常关键的架构与工程经验：

一、数据流体系：从封闭单向管道转向双向数据赋能

当前 Obact 的痛点：
目前工作流的设计把动作（Act）当成了纯粹的副作用派发，执行后只返回成功或失败状态，没有通用的机制把执行产生的数据带出来给后续步骤使用。而抽取（Extract）又是独立    
且笨重的固定表格管道，导致想在中间算个日期、截取前 5 条或做字段清洗时，工作流完全无法承载。

可以学到的设计：
MCP 把每个工具都看作数据生产者。evaluate_script 既可以在页面执行代码，又支持将结果作为对象直接返回给上下文，甚至支持直接传入 filePath
参数一步将计算结果保存到指定文件。
对 Obact 的启发是：
1. 可以在工作流中为动作增加 as 变量绑定语法，比如允许在步骤中执行脚本并将其返回值存入后续步骤可用的变量字典中；
2. 为轻量数据保存提供直接写入磁盘的简易通道，不再强迫所有数据都要走复杂的 extract 索引导出管道。

二、网络数据捕获：从幕后隐式缓存升级为一等公民查询

当前 Obact 的痛点：
当前框架把网络请求截获做成了内部被动缓存（network.ts），且强依赖 CDP 默认的 Inspector 缓存机制。在处理携程这类复杂的业务时，完整的航班数据其实全在 batchSearch    
接口里，但因为响应体超过了 1MB，底层直接报错缓存被逐出（evicted），框架却没有任何办法让用户直接读取这个接口。

可以学到的设计：
MCP 把网络请求视作标准查询工具。通过 list_network_requests 按类型过滤 XHR 或 Fetch，再通过 get_network_request 按 ID
直取原始响应体，接口直接返回干净规整的数据，完全绕过复杂的反爬 DOM。
对 Obact 的启发是：

1. 将网络接口查询提拔为工作流的一等公民动作，允许显式拦截特定 URL 的完整数据流；
2. 对于超大体积的 JSON 响应，底层由 Node 进程直接流式落地或扩大缓存，解决大包被浏览器逐出丢失的问题。

三、页面感知模型：从 DOM 强行打标转向原生无障碍树快照

当前 Obact 的痛点：
目前的 observe 是遍历全页 DOM 节点强行打上 data-obact-ref
属性进行编号。面对现代大型单页应用（SPA）时，几千个节点导致快照过大被截断，且由于前端页面在不断局部异步重绘，打上的编号极易过时失效。
可以学到的设计：
MCP 的 take_snapshot 直接读取浏览器原生的无障碍树（Accessibility Tree）。它天然过滤掉了纯布局用的嵌套
div、样式容器和垃圾节点，只保留具有实际交互意义的文本和控件，信息密度极高，且生成带全局 UID 的树形结构。
对 Obact 的启发是：
引入无障碍语义树快照机制，不仅能让页面的观察体积缩减 80% 以上彻底杜绝截断，还能提供更稳定的语义化节点引用，大幅提升复杂页面的定位成功率。

四、等待与就绪判断：从盲目等待转向 DOM 稳定度检测

当前 Obact 的痛点：
自动化在遇到骨架屏、分批延迟渲染（如前文分析的卡片外壳已渲染、航班号文字延迟填入）时，简单的 wait_for 往往误以为页面已经加载完毕，导致提前抓取到空数据。

可以学到的设计：
MCP 在 evaluate_script 中内置了 waitForStableDom 机制：在执行操作前，自动在页面底层监听微任务队列和 DOM
突变（MutationObserver），只有确认页面在短时间内没有连续的高频变动、真正处于静止状态时才开始读取数据。
对 Obact 的启发是：
在核心执行器层加入 DOM 稳定度探测能力。在执行数据抽取或关键点击前，自动判断页面是否静止，从根源上消灭字段尚未填入的幽灵状态。

五、两者的融合之道：取其所长，补其所短

MCP Chrome 的优势在于工具颗粒度极佳、双向数据流顺畅、与现代浏览器底层机制高度贴合，非常适合智能体进行探索和即时决策；但它缺少长流程所需的任务治理机制。

而 Obact 拥有 MCP 完全没有的王牌武器：断点续跑（Checkpoint）、崩溃自愈监督（Supervisor）、单次提交防重入（once_only）。
