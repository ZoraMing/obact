## 2. 工作包

按依赖排序。“并行”指同一批里可以同时让不同 agent 做（本环境同时跑 2 个 agent 比较稳，4 核）。

| 包 | 内容 | 前置 | 验收 | 估计 |
|---|---|---|---|---|
| **W0 收尾** | bench 任务进 CI；联网的 `--live` 手动任务；文档里把 M1 标成完成 | — | CI 绿 | 小 |
| **W1 runner** | 见 3 节 | — | 假执行器单测（约 12 项）覆盖控制流、重试、once_only 全分支、续跑、跳过模式 | 大 |
| **W2 Lab 大表与文件区**（并行于 W1） | 见 4 节 | — | Lab 自带冒烟（约 8 项） | 中 |
| **W3 CoreExecutor + CLI**（并行于 W1 的后半） | `executor.ts`：act → `core.act`、extract → `extract.ts`、check → 复用后置检查、`actionSeq` → 接口缓存；`cli.ts`、`index.ts`；监督进程信号处理 | W1 的接口稳定（runner 对 Executor 的调用方式） | 能用命令行跑一个小工作流 | 中 |
| **W4 端到端** | 8 项出口用例，见 5 节 | W1、W2、W3 | 全部通过 | 大 |
| **W5 评审与修复** | 对 core 与 workflow 做一次评审，逐条验证后修复 | W4 | 评审零阻塞项 | 中 |
| **W6 收口** | 文档（DEV_PLAN、README 用法、workflow 示例）；`bench`、`e2e` 纳入 CI | W5 | CI 全绿，tree 干净 | 小 |

建议顺序：W0 → (W1 ∥ W2) → W3 → W4 → W5 → W6。W1 与 W2 互不依赖，是唯一值得并行的一对；W3 要等 W1 的接口定下来再开；W4 的几项之间互相独立，可以 2 路并行。

估计用相对量（小：1~2 个 agent 小时；中：3~5；大：6~10），总计约 25~35 个 agent 小时，墙钟约 1.5~2 天的开发节奏（受并发 2 个 agent 与 CI 往返限制）。这个数字有较大的不确定性，主要来自 W1 与 W4：端到端阶段暴露的问题数量，参考 M1 的经验——夹具与 Lab 测试一共揭出了 12 个内核问题。**W4 内预留约 30% 的时间给“端到端暴露的问题”**。

## 3. W1 runner 的实现要点

下列决策已在 DESIGN.md 中定下，runner 严格按它实现，不再讨论：

1. **步骤即动作**：渲染模板 → 去掉步骤字段 → `Executor.act`。控制流步骤（loop_begin / loop_end / break / if / else / end_if / call / set_var / checkpoint）与 `extract` 由 runner 处理。
2. **失败处理**：先按 `retry` 重试，再按 `on_fail`（stop / skip / human）；`once_only` 永不自动重试，忽略 `retry`。
3. **单次提交**：执行前查 `side_effects` 里的幂等键（已有则 `skipped`）；先写检查点再执行；结果分三类——成功（写 side effect）、已发出未确认（写 unverified，绝不重试）、未发出（按普通失败）。错误码到类别的映射以 DESIGN.md 第 7 条为准。
4. **跳过模式**：`on_unverified: skip` → 记待核实 → 重置页面（重放前置路径并满足循环 `anchor`）→ 下一条；连续 2 条状态未明则停止。
5. **续跑**：读检查点 → 恢复 `vars`、`loop_index`、`cursor` → 无条件重放 preamble → 跳到检查点所在位置；检查点停在 once_only 步骤中间且无 side effect → 按崩溃记 unverified。
6. **敏感值**：被脱敏的循环变量不从检查点恢复，续跑时由 `over` 与 `loop_index` 重新渲染。
7. **输出**：`extract` 的行进 `Output`（日期目录在运行开始时固定并写入检查点）；先写数据再写索引。

接口约束：runner 只依赖 `types.ts` 的 `Executor`，不引用 core。这样 W1 可以全部用假执行器测，不需要浏览器，速度快、稳定。

## 5. W4 出口用例

| 用例 | 内容 | 数据源 | 要点 |
|---|---|---|---|
| BW-1 | 50 页 1000 条，主键为详情链接，导出 CSV；第 23 页崩溃后续采结果与不崩溃完全相同 | Lab 大表（分页） | 1000 条、零重复；CSV 带 BOM |
| C-3 | 采集中断：BW-1 第 23 页结束进程，续采零重复零遗漏 | 同上 | 用 `hooks` 或 SIGKILL 子进程 |
| BW-2 | 接口截获与页面滚动各收集一次，两边都是 100 条且内容一致 | Lab 大表（滚动） + 夹具的快响应 / 轮询 | 验证“动作之后到达”的序号机制，包含响应早于抽取步骤的情形 |
| BW-10 | 虚拟滚动大表 1 万条：页面滚动与接口截获各跑一次，内容一致 | Lab 大表 | 性能：要定个上限（暂定每种方式 ≤ 3 分钟） |
| BW-9 | 按订单号逐条审核 500 条，期间注入提交超时；服务端零重复；状态未明进入待核实；跳过模式下其余照常完成 | Lab 订单后台 + `commit_timeout` | 以 Lab 服务端的幂等键计数为判据，而不是引擎自己的记录 |
| C-4 | 提交后超时（已落库不返回）：标记状态未明、不重试、默认停止并提示 | Lab 订单后台 | 对比 `side_effects` 与服务端提交数 |
| C-5 | 连续两条提交超时：跳过模式下第二条后停止 | Lab 订单后台 | 验证“连续 2 条”的计数在中间成功一条后会清零 |
| C-1 | 随机时刻 SIGKILL 子进程：监督进程拉起，重放前置路径，从检查点续跑，最终结果与不被杀一致 | 订单批量 + 采集各一份 | 随机点用固定种子，失败可复现；PRD 的“20 次注入”放进 M4 的浸泡，M2 做 5 次 |

通用判据：每个用例结束后检查 **服务端状态**（Lab `_lab/state`）与 **引擎产物**（`data.jsonl`、`side_effects.jsonl`、`unverified.jsonl`）互相对得上。这是整个 M2 最有价值的断言。

## 6. 评审与质量门

- 每个包合并前：`npx biome check .`、`npx tsc -p .`、受影响目录的测试全绿。
- W4 全部通过后做一次评审（W5），范围：`packages/workflow`、`core/act` 与 `core/network`。对每条发现做“能否构造出真实调用路径触发”的验证，路径不成立的不修，记录原因。
- 沿用“少而有价值”的原则：W1 的假执行器单测约 12 项、E2E 8 项、Lab 冒烟约 8 项；不为覆盖率补测试。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 完整 Chrome 点击导航后输入失效（有头 / 新无头） | 有头模式下的 C-1 / BW-9 可能不稳 | M2 的 E2E 一律用 chrome-headless-shell；有头在真实桌面确认前，文档注明“有头模式未验证” |
| 新标签页接口缓存竞态（新开页面在附加前到达的响应会漏） | BW-2 在新标签页场景可能漏条 | 已知变通：新开页后先 `cache.ready()` 再导航；根治需要 `Target.setAutoAttach` 或在页面登记处挂钩，放进 W3 处理，不行就在文档写明限制 |
| 监督进程 + SIGKILL 的测试依赖进程与文件系统时序 | C-1、C-3 可能不稳 | 子进程用确定性钩子（第 N 步后 `process.kill(process.pid,'SIGKILL')`）加一次真随机；心跳间隔在测试里调小 |
| BW-1 / BW-2 公开站点版本无法在容器验证 | 出口只能“本地版通过” | 联网手动任务；出口文档里分开标注 |
| runner 复杂度（单次提交 × 跳过模式 × 续跑的组合） | 漏掉分支，单次提交重复 | 假执行器单测按“错误码 × 是否 once_only × 模式”做表驱动，不靠手写零散用例 |
| 估时偏乐观 | 超出一两天 | W4 预留 30%；如超出，先保 BW-9、C-1、C-4、C-5（单次提交与崩溃恢复，是产品的核心承诺），BW-10 的 1 万条性能指标可降级为 2000 条 |

## 8. 暂不做（留给后续里程碑）

- 真正的人工接管（`need_human` 在 M2 等同暂停）→ M3。
- 弹窗规则、签名、参数库的实时询问与保存 → M3。
- 完整熔断、卡住截图、运行报告、资源采样 → M4。
- JSON-RPC 服务与 Python 客户端 → M4。
